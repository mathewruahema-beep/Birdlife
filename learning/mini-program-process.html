A plain-English field guide

Building ANWA as a WeChat Mini Program

Everything in the investigation handoff, translated into ordinary language: what a Mini Program actually is, why this project could be stopped before it starts, what has to be decided, and how to run the whole thing without getting burned.

1 · The big picture

A Mini Program (小程序) is an app that lives inside WeChat. Users never visit an app store — they search, scan a QR code, or tap a share, and the app opens instantly inside WeChat itself. For an education business in China this matters enormously, because WeChat is where your students already are.

The critical decision, already made: this is a real, separate app — not the website wrapped in a frame. A wrapper was considered and rejected. That one sentence explains almost everything that follows, because a Mini Program is a separate world with:

  • its own login system (not the website's),
  • its own payment rail (not the website's),
  • its own release process — every version is reviewed by Tencent before the public sees it,
  • its own regulatory review, stricter than anything the website faced.

What it shares with the website is the data and the business rules: the same courses, the same students, the same prices. The art of this project is sharing those things exactly once, while accepting that the front end is new.

What already works. The website has already been moved onto Chinese infrastructure — server in Guangzhou, Chinese database, WeChat login proven, WeChat Pay wired up, ICP filing done. The Mini Program builds on that foundation; it does not repeat it.
The current stage is investigation, not construction. The deliverable right now is a written recommendation — a document, not code. Building starts only after the two "gate" questions in section 3 are answered, because either one can invalidate the whole plan.

2 · The players — three WeChat accounts, and the humans behind them

ANWA owns three separate WeChat properties. They look similar, they are all real, and confusing them once cost a full day. Think of them as three different storefronts with three different keys:

Official Account

Website App

Mini Program

wxa771184f0d69e0e4		 This project. The in-WeChat app to be built. Registered — but nobody has ever looked inside its admin console. Doing that is task one.

Now the humans. This is the single biggest source of delay, so learn it cold:

  • The client controls the WeChat admin consoles. Leroy is only an operator on the Official Account — he cannot see secrets, change core settings, or touch payment configuration.
  • The merchant platform is a fourth, separate system (pay.weixin.qq.com) with its own logins. Nobody on the dev side has access at all.
  • Anything needing core settings, an AppSecret, or merchant configuration must be scheduled with Terry or the account administrator. Every such request is a multi-day round trip. Batch them.
Hard-won tip. You cannot tell from the outside whether a WeChat app ID is an Official Account or a Mini Program — probing anonymously gives the same error for both. Only the console (or the secret key) tells you. Get console facts before writing code; three release cycles were once wasted on a question the console answered in seconds.

3 · The two gates — questions that can kill the project

Before any code, two questions must be answered. These are not details; either one can send the team back to the drawing board.

Gate 1 — Is ANWA even allowed to sell courses in a Mini Program?

Every Mini Program must declare a service category (类目), and education/training categories demand qualification papers — typically a private school operating permit (办学许可证) issued to a mainland Chinese company. Selling courses under the wrong category gets the app taken down. The Official Account being certified proves nothing here — different platform, different review. Must establish: which category ANWA's content falls under, whether the owning entity holds the papers, and — if not — whether an information-only app (no enrolment, no payment) still meets the business goal.

Gate 2 — Do all three WeChat properties belong to the same company?

WeChat gives each user a different ID in each property — unless the properties are bound under one Open Platform (开放平台) account, in which case the user also gets a shared UnionID. That UnionID is the mechanism for recognising "this Mini Program user is the same student who enrolled on the website." If the properties sit under different companies, identities can't be linked automatically (students would have to re-verify by email), and connecting the payment account becomes slow. Confirm all three app IDs sit under one Open Platform account; if not, binding them is a prerequisite, not a footnote.

Everything else in this guide assumes these gates open. If Gate 1 closes, the project changes shape entirely (informational app, or no app). If Gate 2 closes, timelines stretch and the login design changes.

4 · Deciding scope — most of the website stays on the website

Mini Programs are deliberately constrained: the core download is capped at 2 MB (20 MB total with add-on packages), fonts and web features are restricted, and every release waits for review. You do not port a whole learning platform into that box.

The website's surface is huge — catalogue, enrolment, checkout, video player, assignments, quizzes, discussions, certificates, instructor tools, admin, CMS, support, referrals. The handoff's working hypothesis for version 1, to be challenged rather than accepted:

  • In: browse courses · enrol and pay · watch lessons · track progress
  • Out: everything instructor-facing and admin-facing — that stays on the web.

The recommendation document must state the v1 scope and the reasoning for every exclusion. "Small on purpose" is the posture: each feature added is more review surface, more package weight, and more compliance exposure.

5 · The technical calls, in plain English

How the app talks to the server — the main decision

The website's front end and back end speak a private dialect (tRPC) that assumes a browser with cookies. A Mini Program has neither. Three options are on the table:

  • Build a small, purpose-made API inside the existing server for the Mini Program, reusing the business logic underneath. (The handoff leans here.)
  • Force the website's dialect into the Mini Program — possible, but fights the platform.
  • Build a whole second backend — almost certainly overkill, and dangerous: two copies of pricing or enrolment rules will drift apart.

The iron rule regardless of choice: business logic lives in exactly one place. The migration already demonstrated what divergence costs — a stale cached component silently blanked a homepage section for hours.

Login is a different mechanism, same identity

Website login: WeChat asks the user's permission → website gets a session cookie. Mini Program login: the app calls wx.login() → gets a one-time code → the server trades it with WeChat for that user's Mini Program ID. No cookies; the app keeps its own token in storage.

The identity questions: can the existing session system issue tokens for this new kind of client? And how does a returning website student get recognised? The clean answer is the UnionID (Gate 2); the proven fallback is the email-verification link step the website already uses. One schema fact to remember: the same person has a different WeChat ID in the Mini Program than in the Official Account — the database already has a column for the shared UnionID, but storing the second per-app ID needs a decision.

Payment — same engine, different registration

Mini Program payment is its own rail: same underlying WeChat Pay machinery the website will use, but bound to the Mini Program's app ID and triggered by an in-app call. The existing payment adapter already does the hard parts (signing, decrypting notifications, offline tests). The blocker is administrative, not technical: the merchant account (商户号) must be linked to the Mini Program's app ID, which needs both the merchant super-admin and the app administrator — i.e. the client, i.e. latency. Start that early.

Video — check it before believing it

Course video sits on Tencent's video service. Confirm early that it plays inside a Mini Program — player component, signed URLs, and whether the anti-piracy setup carries over. This is a classic late-project ambush; the handoff says check it first, not last.

Framework — native or translated?

Two philosophies: write in WeChat's own native language (closest to the platform, zero code shared with the React website), or use a translation layer like Taro or uni-app (React-flavoured, some sharing, plus a new category of bugs). The handoff's warning: be sceptical of "we can share components with the website" — in practice sharing ends at types and pure logic, and over-claiming costs more than it saves. Weigh the team's actual skills, then recommend.

6 · Review, compliance, and how releases actually work

This is the part with no equivalent in Western web development, so it deserves its own mental model:

  • Every release is reviewed by Tencent. Turnaround is days, not minutes. You cannot hotfix your way out of a mistake the same afternoon. Release planning must absorb this.
  • A privacy declaration is mandatory. Since 2023, a Mini Program must declare what personal information it collects (隐私协议) before it may even call the APIs that touch that data. Not optional; blocks release.
  • There are safe testing lanes. A developer version (开发版) and a beta/trial version (体验版) let the team and the client test on real phones without any public release or review. Use them; never test in production.
  • China's privacy law (PIPL) applies to everything collected, exactly as it already does for the website.
Rhythm to internalise: build → developer version (team phones) → beta version (client's phones) → submit for review → wait days → public release. Plan features in batches sized to that cycle.

7 · The process, end to end

Here is the whole journey as one ordered sequence. Steps marked in red are the gates. "Client" means Terry or the account administrator — the people with console access.

  1. Open the Mini Program console and record the facts

    The app ID exists but its console has never been examined. Establish: registered to which company, what category, what state.

    Needs: client console access · Output: facts, before any code

  2. Gate 1 — category qualification

    Which education category applies, and does the entity hold the permit? If not: what's the fallback, and does it still meet the goal?

    Needs: client documents · Can invalidate the whole plan

  3. Gate 2 — one company, one Open Platform account

    Confirm all three WeChat properties are bound together so users share a UnionID and payment binding is simple.

    Needs: client console access · Changes login design and timeline if closed

  4. Write the recommendation document

    Seven sections: feasibility verdict · v1 scope with exclusions · API decision · login & identity design · framework choice · phased effort estimate · risk list (what forces a rebuild vs. a fix). Lives in docs/.

    Needs: gates answered · This is the current workstream's actual deliverable

  5. Start the slow administrative clocks

    Merchant-account-to-app-ID binding; Open Platform binding if missing; qualification paperwork if missing. All client-side, all slow — start them the moment the plan is approved.

    Needs: client + merchant super-admin · Runs in parallel with build

  6. Build v1 against the plan

    Small scope: browse, enrol, pay, watch, track. Business logic stays in its one home on the server. Video playback verified early.

    Needs: dev team · On its own branch; production stays quarantined

  7. Test in the safe lanes

    Developer version on team phones, then beta version on the client's phones. Privacy declaration filed before APIs that need it.

    Needs: dev + client testers

  8. Submit for review, wait, release

    Days of turnaround per release. First release proves the pipeline; iterate in batches thereafter.

    Needs: Tencent review · Repeats for every version forever

8 · Managing it — the three rules that keep you safe

Rule 1: Facts before code. Every question that a console screen can answer should be answered there, not by experiment. Log what you find; the handoff exists because console facts were expensive to rediscover.

Rule 2: Respect the latency of the client. The critical path of this project is not engineering — it is access. AppSecrets, merchant settings, qualification documents all route through Terry or the administrator. Manage it like a supply chain: batch requests, ask early, always have engineering work that isn't blocked on them.

Rule 3: Nothing touches production. The production quarantine from the migration is still active. This work lives on its own branch, and testing happens in the Mini Program's developer/beta lanes — never on the live site or a live release.

And the posture for the current phase: you are producing a recommendation. Resist the pull to start building; the gates exist precisely because building first has a known failure mode here (an app that can never legally launch, or users who can never be recognised).
